# GenOffice Project — PROJECT-017 MPP Adapter Feasibility Report

Status: INVESTIGATION (no production MPP implementation — this document is the deliverable)
Scope: PROJECT-017 only. Nothing in this report authorizes PROJECT-018/019 implementation.
Investigation environment: sandbox with OpenJDK 21.0.11, Node 24.18.0, network access to Maven Central / GitHub / npm (all commands reproducible; see §11 and §20).

---

## 1. Executive conclusion

**MPP import is feasible through an MSPDI intermediary, executed by an external MPXJ-based conversion process owned by the host — not by a parser inside the foundation packages. MPP export is NOT feasible under the current architecture, licensing constraints, and ecosystem.**

The evidence:

1. The `.mpp` format is **not publicly specified**. Microsoft publishes the container spec ([MS-CFB], the OLE2 Compound File Binary format) but not the proprietary streams inside it. All non-Microsoft MPP knowledge comes from partial reverse engineering; the maintainer of MPXJ — the most complete open-source MPP reader in existence — states the knowledge of the file structure is "still relatively incomplete" and that MPXJ therefore **cannot write MPP at all** [S1, S2].
2. A real, isolated spike (§11) proved the full import pipeline mechanically end-to-end on **real MPP files across MPP8/MPP9/MPP14**: `MPP bytes → MPXJ 16.7.0 (Java) → MSPDI XML → the accepted PROJECT-015 importer → canonical ProjectDocument`, deterministically. Four concrete convention mismatches were identified and must be normalized by the future adapter (they are enumerable and mechanical — §10).
3. **No pure-JavaScript/TypeScript/WASM open-source MPP parser with meaningful coverage exists** (§5): npm offers only (a) `@byteink/mppjs`, an MIT wrapper shipping MPXJ as a GraalVM AOT native binary — import-only, v0.1.x, and it **failed to run in our headless sandbox** (`UnsatisfiedLinkError: No awt`) — and (b) `@tensor-estate/tsmpp`, a minimal Bun-only TS parser extracting a shallow subset (names, hierarchy, predecessors, baselines, columns), v0.1.0, synthetic tests only.
4. **MPP writing** is available only through (a) Microsoft Project itself (COM automation on Windows with an installed, licensed Project — undistributable), or (b) commercial SDKs (Aspose.Tasks, from US$1,797/year per developer OEM [S10]). No open-source MPP writer exists anywhere.
5. The frozen architecture (`spec/project/architecture-lock.md` §13) forbids foundation packages from importing `.mpp` parser implementation code. An MPXJ-based adapter therefore **cannot live inside `packages/project-file`**; it must be a host-managed sidecar behind a foundation-defined adapter contract. This requires **no change to architecture-lock.md** (§14) — the lock constrains foundation packages, not host-level integration.

Formal decision (see end of document for the required closing line): **FEASIBLE — MSPDI/INTERMEDIARY ADAPTER** (import-only; MPP export rejected — §17, §18).

## 2. Format overview

- `.mpp` is Microsoft Project's native binary format (`.mpt` for templates). Since the Project 2000 era it is a **Compound File Binary (CFB, aka OLE2 structured storage) container** [S3, S4] — a small filesystem-in-a-file with streams and directories. The container is publicly specified as [MS-CFB] by Microsoft [S4]. Spike verification: every downloaded corpus file begins with the CFB magic bytes `D0 CF 11 E0 A1 B1 1A E1` (§11).
- The **streams inside the container are proprietary and undocumented by Microsoft**. What is known comes from community reverse engineering, concentrated in MPXJ (its `org.mpxj.mpp` package, its "MPP Field Guide" documentation, and Apache POI's POIFS layer for the container) [S1, S5].
- MPP stores: project properties; tasks (WBS/outline, dates, durations, constraints, deadlines, priorities, notes, custom fields); dependencies; calendars (working weeks + exceptions, inheritance); resources (work/material/cost, rates, availability); assignments (work/cost/units); baselines (up to 11 slots); views/tables/filters/groups **and other presentation data**; timephased data; subproject links; resource pools; enterprise-specific fields (Project Server); VBA macros (as embedded OLE streams); and password protection (MPP9 files are partially encrypted; later versions use a protection flag) [S1, S6].
- Key asymmetry: presentation/appearance data (views, tables, bar styles, filters) is readable from MPP but, per MPXJ's maintainer, **no writable format — MPP included, for MPXJ — can carry it back**; MSPDI does not represent it [S2].

**MPP is NOT equivalent to MSPDI on a container level** (binary CFB vs XML), and feature-parity is partial: MSPDI carries the semantic data model but not presentation data, raw timephased blobs, macros, or enterprise fields the same way MPP does.

## 8. Security analysis

MPP files are **untrusted binary input**:

- **Malicious/malformed binary structures**: the CFB layer and proprietary streams are parsed by MPXJ/Apache POI — a mature but non-trivial Java attack surface (historical POI CVEs exist for compound documents). Mitigation: run conversion in an **isolated sidecar process** with no network access, no filesystem access beyond the single input file and output path, a hard wall-clock timeout, and memory limits (`-Xmx`). A crash/exploit in the parser is then contained; the main process only ever handles XML output that passes through our already-hardened PROJECT-015 parser (byte caps, depth caps, entity guards).
- **Decompression bombs**: MPP is not archive-compressed as a whole; POI's CFB layer is sector-based. Memory exhaustion remains the realistic DoS vector → sidecar `-Xmx` cap + input size cap (mirror `MSPDI_MAX_INPUT_BYTES` discipline) + timeout.
- **Native-code attack surface**: the GraalVM AOT binary route (@byteink/mppjs) adds a 66 MB unsigned native executable per platform to the supply chain — larger blast radius than a jar + JRE, and the spike showed it can fail to even start on minimal systems. **Recommendation: prefer jar+JRE sidecar; if a native packaging is ever adopted, it must be built from source in CI and checksum-pinned.**
- **VBA/macros**: MPP can embed macro projects. The intermediary path **never executes** MPP content (MPXJ reads data, does not run macros); macros are simply not represented in MSPDI → diagnosed loss, zero execution risk. This must stay true in PROJECT-018 (no macro pass-through of any kind).
- **Password-protected files**: MPP9 encryption is bypassable without the password [S6] — treat as accessible; other versions raise `MPXJException` → surfaced as a diagnostic (feature, not a bug: we do NOT attempt password cracking beyond what MPXJ's documented behavior provides).
- **Supply chain**: MPXJ is downloaded from Maven Central (checksums via the repo) and must be version-pinned in the sidecar manifest. LGPL compliance artifacts (source offer) ship alongside.
- **Sandbox requirement**: the eventual importer must be safe to run against attacker-controlled files _by construction of the process topology_ — the security model is the sidecar boundary, which PROJECT-018 must specify precisely before implementation is authorized.

## 10. MSPDI intermediary analysis

Pipeline: `MPP → MPXJ (MSPDIWriter) → MSPDI XML → PROJECT-015 importer → ProjectDocument`. Reverse (export): `ProjectDocument → PROJECT-016 exporter → MSPDI → MPP` — **the last hop has no open-source implementation** (§5), so the reverse intermediary is not available; PROJECT-016's MSPDI output remains the interchange endpoint.

The spike (§11) proved the forward pipeline on real MPP8/9/14 files and enumerated the exact semantic gaps between MPXJ's MSPDI conventions and our accepted importer. Five normalizations, all mechanical, all to be owned by the future MPP adapter (NOT by weakening the importer):

| #   | MPXJ/MSPDI convention                                                                                               | Our importer today                                                                                                                           | Required normalization (adapter-owned)                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| N1  | `CalendarUID -1` / `BaseCalendarUID -1` = "none" sentinel                                                           | treated as dangling reference → `INVALID_MSPDI_REFERENCE` / `MISSING_BASE_CALENDAR` errors (recovery to default calendar is already correct) | strip `-1` references before import (they mean "inherit the default")                                                     |
| N2  | (root cause of N1 errors) —                                                                                         | —                                                                                                                                            | same pass                                                                                                                 |
| N3  | hidden placeholder task with `UID 0` / `OutlineLevel 0` / `WBS "0"` (MPP summary artifact, documented by MPXJ [S2]) | imported as task `t0` → engine `INVALID_OUTLINE_LEVEL`                                                                                       | filter the placeholder task (and the analogous null-name placeholder resource) before import                              |
| N4  | `WorkingTime` periods wrapping midnight emit `ToTime 00:00:00`                                                      | rejected as inverted (`INVALID_MSPDI_CALENDAR`, period dropped)                                                                              | rewrite `ToTime 00:00:00` → end-minute 1440 (canonical `endMinute: 1440` is engine-valid); alternatively split the period |
| N5  | "unassigned" assignments emitted with `ResourceUID -65535`                                                          | dropped as dangling reference (error diagnostic)                                                                                             | pre-filter with a dedicated expected-loss diagnostic (canonical model has no unassigned assignment)                       |

Post-normalization, the remaining known intermediary losses are exactly the accepted MSPDI boundary losses (documented in PROJECT-015/016): recurring exceptions → single-date + warning; `physicalPercentComplete` not read back; notes collapsed; `task.baseline` reverse index reconstructed empty; views/tables/filters/groups not represented. **These are all already diagnosed behaviors of accepted, reviewed code — the intermediary adds no new silent loss.** The spike further showed the pipeline is deterministic: re-importing the same MSPDI bytes produces byte-identical canonical documents (§11).

Conclusion: the intermediary is viable; the loss profile is acceptable _and diagnosable_; the normalization layer is small, testable, and adapter-local.

## 12. Determinism analysis

- **Read path**: `MPP bytes → MPXJ → MSPDI`: the spike re-imported identical MSPDI bytes to byte-identical canonical documents; MPXJ's read/write path is a pure in-memory transformation (no clock/randomness involvement in data extraction). A repeat-run re-conversion of all 7 corpus files (spike re-verification) shows the generated MSPDI is byte-identical across runs **except for exactly one element: the `<CurrentDate>` save timestamp written by `MSPDIWriter`** — every task/calendar/resource/assignment/baseline byte is stable. The accepted PROJECT-015 importer does not read `<CurrentDate>` at all, so canonical documents are byte-identical across conversion runs. PROJECT-018 must still add an explicit repeat-run byte-equality proof over the corpus (the accepted PROJECT-014/015/016 pattern), because MPXJ itself carries no such guarantee contract — and its save-timestamp behavior means that proof must be asserted at the canonical-document level, with `<CurrentDate>` treated as non-semantic (strip-or-ignore in the normalization layer).
- **Canonical post-processing**: the N1–N5 normalization layer is pure TS and deterministic by construction (same input → same output; no `Date.now()`, no locale).
- **Write path (MPP export)**: no open-source writer exists; commercial writers (Aspose) do not document determinism, and Microsoft Project itself stamps save timestamps — canonical MPP bytes are effectively unattainable. **This is a contributing reason MPP export is rejected** (§17, §18).

## 13. Performance considerations

- Spike observations (Java 21, this sandbox): whole-pipeline cost dominated by JVM startup (each sidecar invocation ~1–3 s wall); in-process parse+MSPDI-write of the 100–250 KB corpus files completed in the sub-second range; our TS import+validate+schedule of the resulting MSPDI ran 11–172 ms per file in vitest.
- Scaling expectations (Java heap-based POI/MPXJ model): 100 tasks — trivial; 1,000 tasks — comfortable; 10,000 tasks — fine (tens of MB heap); 100,000 tasks — feasible with raised `-Xmx`, but memory becomes the bottleneck (full in-memory `ProjectFile` model + POIFS); MSPDI XML size grows superlinearly in edge-heavy files. The sidecar topology isolates this cost from the UI process regardless.
- Required benchmark work for PROJECT-048 (NOT authorized now): corpus-driven timing at 100/1k/10k/100k tasks through the full pipeline; sidecar cold/warm start; MSPDI size vs. task/dependency counts; normalization-layer overhead; memory ceiling of the sandboxed sidecar.

## 14. Architecture impact

- **No change to `architecture-lock.md` is required** for the recommended strategy. The lock's relevant invariants remain intact:
  - §3/§10 — `packages/project-file` remains the file-adapter boundary; the MPP adapter reuses the existing `ProjectFileAdapter`/`ImportDiagnostic` contracts; no second canonical model; MPP-specific structures stay adapter-local.
  - §13 — foundation packages must not import `.mpp` parser implementation code: **satisfied by construction** — the foundation package will contain only the adapter _contract_, the MSPDI-side _normalization layer_ (pure TS, operating on MSPDI XML, analogous to the accepted pure-TS MSPDI tokenizer), and diagnostics. The MPXJ conversion process is a **host-level sidecar** (desktop host / server service), outside all foundation packages.
  - §5 — the canonical time model is untouched (integer working minutes, UTC ISO timestamps) — the intermediary feeds the accepted MSPDI importer, which already normalizes to canonical semantics.
- The one genuinely new architectural element is the **host-injected converter channel**: the foundation-level `MppAdapter` (PROJECT-018) would define an interface for "bytes + a host-registered conversion channel → MSPDI bytes", with the host wiring the MPXJ sidecar. If the Principal Architect instead prefers the MPP adapter to be wholly in-`project-file` (impossible for MPXJ per §13) or wholly host-side, that is a scoping decision to record at PROJECT-018 kickoff — flagged as an open question (§19), NOT silently decided here.
- The renderer/Electron/browser layers gain nothing to parse (§7) — browser-based MPP import must be mediated by a host/server conversion endpoint, preserving the architecture-lock §13 boundary.

## 15. Recommended strategy

**Adopt the MSPDI-intermediary import adapter with an externalized MPXJ sidecar:**

1. **PROJECT-018 (MPP import)**: implement in two parts — (a) a pure-TS `MppAdapter` boundary in `packages/project-file`: contract, N1–N5 normalization layer over the MPXJ MSPDI output, expected-loss diagnostics, determinism/round-trip tests against the external corpus; (b) a host-level conversion sidecar spec (MPXJ 16.x pinned, jar+JRE, sandbox profile: no network, `-Xmx` cap, timeout, single-file I/O) — the sidecar ships with the desktop product and an optional server service. MPP import becomes a Tier-A/B feature set (§9) with Tier-C/D diagnosed losses.
2. **PROJECT-019 (MPP export)**: **rescope** — do NOT implement MPP writing. Either (a) close it as "not feasible under current architecture/ecosystem" with PROJECT-016's MSPDI export as the sanctioned Microsoft interchange path and a clear `UNSUPPORTED_MPP_FEATURE` diagnostic for `.mpp` save requests, or (b) explicitly re-open it only as a business decision to license Aspose.Tasks (US$1,797+/yr/developer [S10]) — in which case it needs its own feasibility round. Recommendation: (a).
3. Licensing posture: LGPL compliance kit for MPXJ (license text + source offer) shipped with the sidecar; no copyleft contamination of proprietary code via the process boundary (§6).
4. Security posture: §8 sidecar topology is a _precondition_ for PROJECT-018 authorization.

## 18. Explicit rejected alternatives

1. **In-house pure-TS MPP parser/writer** — unknowable-effort reverse engineering; no writer attainable; tsmpp demonstrates the shallow ceiling [S9].
2. **In-process MPXJ inside `packages/project-file`** — impossible: Java library + architecture-lock §13 forbids foundation packages importing MPP parser implementation code.
3. **@byteink/mppjs as the production dependency** — young (v0.1.x), headless-Linux failure in our own spike, 66 MB native sidecar supply-chain surface, LGPL-static-AOT compliance murk (§5, §6, §8, §11). May be revisited as an optional user-side convenience only.
4. **Aspose.Tasks (commercial SDK)** — the only MPP writer, but cost, closed source, and sidecar-in-another-runtime; rejected as default, documented as the conditional MPP-export path (§17).
5. **Aspose Cloud / any conversion SaaS** — privacy (user files leave the machine), recurring cost, no offline operation.
6. **CheerpJ browser-WASM MPXJ** — commercial runtime license [S15] + massive payload; browser MPP import goes through the host/server instead.
7. **Microsoft Project COM automation** — per-machine Project license; Windows-only; non-deterministic writes; undistributable.
8. **LibreOffice-mediated conversion** — LibreOffice has no MPP support at all [S16].
9. **"Parse some MPP bytes" as feasibility** — explicitly rejected per the brief; the spike's value is the _end-to-end pipeline proof + enumerated normalization requirements_, not partial parsing.

## 19. Open questions

2. Whether the Principal Architect wants the `MppAdapter` contract to live in `packages/project-file` (recommended; lock-compliant) or as a host-level interface — scoping decision to record at PROJECT-018 kickoff (§14).
3. Web-host MPP import UX: server conversion endpoint (privacy statement required) vs desktop-only feature.
4. Corpus provenance policy: pinned-download harness (recommended) vs checked-in manifest; legal review sign-off for consuming the LGPL corpus in CI.
5. MPP8 Flag-field defect [S2]: accept as documented Tier-C loss or exclude MPP8 from Tier-A claims.
6. If true MPP export ever becomes a hard requirement: commission a dedicated Aspose feasibility round (cost/locking/EULA review) — explicitly out of scope here.
