# GenOffice Project — PROJECT-019 MPP Export Strategy / Rescoping Report

Status: INVESTIGATION (no production MPP-export implementation — this document and the spec/test updates it ships with are the deliverable)
Scope: PROJECT-019 only. Nothing in this report authorizes an MPP writer, an MPP export API, a commercial SDK dependency, or a COM bridge.
Investigation environment: sandbox with OpenJDK 21, Node 24, network access to mpxj.org / learn.microsoft.com / support.microsoft.com / products.aspose.com / purchase.aspose.com / github.com (all pages retrieved and read as primary sources for THIS investigation — see §19; PROJECT-017's earlier external survey remains cited where its findings are re-verified below).
Baseline: merged main `2aa2b74` (PROJECT-001 through PROJECT-018 accepted, incl. the MPP import pipeline).

## 1. Executive conclusion

**MPP export is deferred: GenOffice's supported write path is `.gproj` (native canonical) + MSPDI (Microsoft-designated interchange). Outcome E of the brief's A–E set.** No viable MPP-export strategy exists today that is simultaneously compatible with GenOffice's zero-commercial-dependency licensing posture, its desktop/web/server/offline runtime matrix, its deterministic-output requirement, and its security policy — except at the cost of an explicit business/licensing decision (commercial SDK) that the Principal Architect has not made and that this report deliberately does not make for them.

The evidence (each item verified against a live primary source for this investigation, §19):

1. **No open-source MPP writer exists.** MPXJ — the ecosystem's most complete open-source MPP implementation, which GenOffice already ships as the import sidecar — states verbatim on its FAQ: _"Can I use MPXJ to write MPP files? Not at present. Although it is technically feasible to generate an MPP file, the knowledge we have of the file structure is still relatively incomplete… You are therefore probably better off using MSPDI which does support the full range of data items present in an MPP file."_ [E1]. The MPXJ site documents write support for exactly MPX, MSPDI, Planner, PMXML, SDEF, and XER — there is no `howto-write-mpp` page (HTTP 404) [E2]. The npm ecosystem offers nothing new: the only MPP packages are the import-only `@byteink/mppjs` MPXJ wrapper and the minimal `@tensor-estate/tsmpp` subset parser, neither of which writes MPP [E18]. LibreOffice has no MPP support at all [E13].
2. **Microsoft itself designates XML (MSPDI) — not MPP — as the interchange format between Project and other programs:** _"You can export and import project data with this format. The XML format can be used to interchange project data between Project and other programs."_ [E5]. Notably, Microsoft's own Project-for-the-web **cannot export MPP at all** [E8], and even Project desktop can no longer save to the 2000–2003 MPP formats [E5] — MPP is a live application format, not a stable interchange target.
3. **The only programmatic MPP writers are commercial or per-seat licensed.** Aspose.Tasks writes MPP **only in licensed (paid) versions** [E9]; current pricing is US$799 "Developer Small Business" (1 developer, 1 deployment location) and US$2,397 "Developer OEM" (1 developer, unlimited deployment locations; "from US$1,797/year") [E10]. Microsoft Project COM automation can save MPP (`PjFileFormat.pjMPP`) [E7] but requires an installed, licensed Microsoft Project on each machine, is Windows-only, and Microsoft explicitly **does not recommend or support server-side automation of Office** [E6].
4. **Deterministic MPP output is unproven for every candidate and impossible for one.** Project's own saves stamp timestamps (PROJECT-017 §12 [E17]); Aspose's closed-source writer documents no determinism contract [E9][E10]; and no post-hoc byte normalizer can exist without an MPP writer to begin with. GenOffice's determinism guarantee — same canonical `ProjectDocument` → byte-identical output — is proven today for `.gproj` (PROJECT-014) and MSPDI (PROJECT-016), and cannot be extended to MPP without a licensed empirical spike that has not happened (§8).
5. **The accepted write path already covers the actual need.** PROJECT-016's MSPDI export is production-grade, deterministic, loss-diagnosing, and opens in Microsoft Project on every format the current Project supports [E5]. The residual gap versus true MPP is presentation data (views/tables/bar styles) — which MPXJ's maintainer confirms **no writable format except MPP can carry** [E1] — plus the psychological "it's an .mpp file" property. That gap does not justify a commercial dependency, a platform-bound feature matrix, or an unverifiable output format.

Formal decision (closing line at end of document): **MPP EXPORT DEFERRED — MSPDI/.gproj IS THE SUPPORTED WRITE PATH** (outcome E; conditional reopening criteria for the commercial-SDK path are documented in §15/§17 and require explicit Principal Architect + business approval).

## 6. Security analysis

Write-path security differs fundamentally from the accepted import analysis: the input to any export converter is **GenOffice's own deterministic MSPDI output** (trusted, produced by the accepted PROJECT-016 exporter), and the output is a binary that a third party will open in Microsoft Project. The threat model therefore concentrates on the CONVERTER PROCESS and the LICENSING/TELEMETRY surface, not on untrusted input parsing.

- **Aspose.Tasks sidecar.** (a) _Process isolation_: would run as another one-shot sidecar exactly like `project-mpp-host`'s MPXJ launcher — this part of the architecture is proven and reusable. (b) _Network dependency_: closed source ⇒ the "no network access" invariant CANNOT be established by source inspection; it would have to be enforced at the OS level, which today exists only as the Linux user+network-namespace wrapper — **Windows and macOS hosts would fail closed under the current `networkIsolation: 'required'` policy**, i.e. an Aspose sidecar would be unusable on the two most common desktop platforms until host-hardening adds mechanisms there. (c) _Metered licensing_: Aspose's pay-per-use model contacts Aspose's metering service by design [E9][E10] — a runtime network caller that contradicts both the offline requirement and the fail-closed isolation posture. (d) _Licensing telemetry / license file_: the OEM license file is embedded in the distributed product — an extraction/cracking target and a supply-chain obligation. (e) _Arbitrary filesystem access_: controllable via the same per-import temp-workspace + single-file-I/O discipline as the accepted sidecar. (f) _Output validation_: possible through GenOffice's own PROJECT-018 import pipeline (the round-trip oracle, §8) — the one genuinely strong security/fidelity tool available.
- **Microsoft Project COM automation.** Launches the full interactive Microsoft Project application on the user's machine: no meaningful process sandbox (it IS the user's app), runs with user privileges, subject to Project's own macro/security model on whatever file it opens, and **Microsoft explicitly does not recommend or support unattended/server-side automation of Office** [E6]. Unattended execution additionally collides with Project's interactive dialog surface (modal prompts, first-run configuration, credential prompts). Not containable to GenOffice's security invariants.
- **Cloud conversion service.** The user's project data would leave their machine to a third party — a **data-exfiltration boundary**. For a desktop office suite this is a privacy and enterprise-procurement blocker, it makes offline operation impossible, and per the brief it would require separate architecture approval even to evaluate. Rejected without further analysis.
- **Status quo (MSPDI/.gproj).** The exporter is GenOffice's own accepted pure-TypeScript code behind the foundation boundary: no process, no network, no third-party code, deterministic output, and no new attack surface. The write path is strictly safer than every alternative considered here.

## 8. Determinism analysis

The requirement: _same canonical `ProjectDocument` → deterministic output._ Established facts:

- **`.gproj`**: byte-deterministic, proven (PROJECT-014 round-trip + golden byte-identity).
- **MSPDI**: byte-deterministic, proven (PROJECT-016: triple byte-equality, reorder invariance, static no-clock/no-randomness source guards, embedded canonical bytes for representative goldens).
- **MPP via Microsoft Project COM**: **deterministically non-deterministic.** Project stamps save metadata (timestamps) — already established as the reason canonical MPP bytes are "effectively unattainable" in PROJECT-017 §12 [E17]. Can the stamps be suppressed/normalized? No: `FileSaveAs` exposes no documented control over the save stamps [E7], and post-processing the binary would require an MPP writer — the very thing that does not exist. Verdict: canonical-semantic determinism only (via the oracle below); byte determinism impossible.
- **MPP via Aspose.Tasks**: **unproven and unverifiable without a license.** The official documentation documents no determinism contract for the MPP writer [E9]; the writer is closed source (no static audit possible); the format's save-metadata behavior under Aspose is undocumented; and output bytes are a function of the Aspose version (closed-source release drift). Can nondeterministic fields be suppressed/normalized/canonicalized/post-processed? No documented mechanism exists for any of the four verbs; post-processing again presupposes a writer. **This report therefore does NOT claim deterministic MPP output, and no future increment may claim it without a licensed empirical proof.**
- **The available oracle (verification design, mandatory for any future approved spike):** GenOffice already owns an MPP reader pipeline (PROJECT-018). Any authorized MPP-export spike must prove _semantic_ determinism by round-tripping: `ProjectDocument → MSPDI → converter → .mpp → (PROJECT-018 pipeline) → ProjectDocument′`, asserting canonical equality of `serializeGproj` bytes across repeated runs — while byte-level `.mpp` equality is measured, reported, and explicitly NOT promised. This is the only honest determinism statement an MPP path could ever make, and it requires the licensed converter first.

## 9. MSPDI intermediary analysis

The pipeline `ProjectDocument → accepted MSPDI exporter (PROJECT-016) → conversion layer → MPP` was assessed field-by-field. What survives the FIRST hop is precisely established by accepted evidence (PROJECT-016's no-silent-loss contract — every limitation is a diagnosed diagnostic, and the round-trip through the accepted importer is byte-identical at the canonical level):

- **Survive exactly (Tier A)**: tasks/name/dates/duration/priority/notes/milestones/summaries; WBS hierarchy (deterministic DFS projection); FS/SS/FF/SF dependencies with minute-precise lag; calendars incl. inheritance and exceptions (with documented normalizations); all eight constraints; deadlines; work/material/cost resources with rates and availability; assignments with units/work/cost; multiple baselines; custom fields; progress.
- **Survive with documented normalization (Tier B)**: inherited partial working weeks (materialized with `MSPDI_EXPORT_NORMALIZED` info diagnostics); non-convention calendar identities (deterministic re-identification); `24:00:00` day-end periods (the accepted PROJECT-015/018 convention).
- **Known diagnosed losses at the MSPDI hop**: `physicalPercentComplete` (not representable); multiple notes collapse to the MSPDI single note; task-level baseline reverse index reconstructed empty on import; presentation data (views/tables/filters/groups) not represented at all; numeric-looking string custom values normalized.
- **The second hop (MSPDI → MPP) is where the intermediary analysis hits the wall**: there is no open-source implementation of that hop (§1), so the composite pipeline exists only as the COM or commercial-SDK packaging (§3 #2). The composite loss profile is therefore the MSPDI losses **plus** the converter's own undocumented delta — for Aspose, a closed-source transformation whose fidelity is only measurable empirically through the §8 oracle.

**Conclusion:** the intermediary is lossless-with-documented-normalization up to the MSPDI boundary and **cannot be called lossless beyond it**. The honest claim ends at "MSPDI is the interchange endpoint"; everything after that is converter-specific and evidence-gated.

## 10. COM analysis

Microsoft Project's automation surface (the `Microsoft.Office.Interop.MSProject` COM interop namespace, incl. `ApplicationClass`/`ProjectClass` and the `PjFileFormat` enumeration whose `pjMPP = 0` member selects MPP in `FileSaveAs`) is fully documented by Microsoft [E7]. Assessed per the brief:

- **Windows-only requirement**: yes — COM automation of a Win32 desktop application.
- **Microsoft Project installation requirement**: yes — the interop assembly is a proxy to the installed application; there is no redistributable automation runtime.
- **Office licensing**: every machine executing the conversion must hold a licensed Microsoft Project; the capability cannot be shipped as a GenOffice product feature (per-seat EULA).
- **Desktop-only nature**: yes by construction.
- **Server infeasibility**: decisive — Microsoft's own guidance: _"Microsoft does not recommend or support server-side Automation of Office"_ (complications under ASP/ASP.NET/DCOM/services: re-entrancy, security context, deadlocks, resource usage) [E6].
- **Sandboxing**: effectively impossible — the automation launches the interactive Project application with the user's privileges; GenOffice's process-isolation invariants (one-shot sidecar, `-Xmx`-class caps, OS-enforced network isolation) have no analogue here.
- **Security**: exposes Project's full attack surface (macros, prompts, COM activation) to whatever document the automation session touches; unattended execution is explicitly the unsupported case [E6].
- **Unattended execution**: modal dialogs, first-run experiences and credential prompts make headless operation fragile in exactly the way the accepted sidecar architecture was designed to avoid.
- **Deterministic output**: no — save timestamps are stamped by Project itself (§8).
- **Web incompatibility**: total — no browser hosts COM; even the server relay is the unsupported-by-Microsoft case.

**Verdict**: COM automation is a technically real, officially documented MPP writer that GenOffice must NOT productize. Its only acceptable role is the user-driven workflow (§3 #9): a user who owns Project opens GenOffice's MSPDI export and saves as MPP themselves — Microsoft's own sanctioned interchange path [E5], zero GenOffice code.

## 11. Commercial SDK analysis

The only programmatic MPP writer on the market is Aspose.Tasks (its Cloud sibling is §6's rejected SaaS path). Documented per the brief:

- **License**: commercial EULA; Developer Small Business (1 developer, 1 deployment location) US$799; **Developer OEM (1 developer, unlimited deployment locations) US$2,397 first year, "from US$1,797/year" renewal** [E10]. Paid support and paid consulting are separate products. (PROJECT-017's US$1,797+/yr figure is thereby current for the OEM renewal class.)
- **MPP write gating**: official documentation — _"Saving project as MPP file is only available in licensed versions"_ [E9]; the evaluation build writes watermarked/limited output instead. Forum guidance confirms a valid license is required to save MPP [E11].
- **Runtime requirements**: .NET, Java, C++, or Python native libraries — a second sidecar runtime for GenOffice (Node/Electron host would spawn a .NET/Java process exactly like the MPXJ JVM sidecar, or embed via Node interop layers that add their own fragility).
- **Platform requirements**: Windows/Linux/macOS across its runtimes — full coverage is available in principle, but each runtime × platform pair becomes a distribution/QA cell GenOffice does not currently pay for.
- **Pricing model**: per-developer with annual renewal for updates/support continuity; **metered (pay-per-use) licensing exists but phones home to Aspose's metering service** — disqualified by the offline + isolation requirements (§6).
- **Server/cloud restrictions**: OEM tier explicitly licenses unlimited deployment locations [E10]; the server-side use itself is technically supported — the restriction is contractual and cost-shaped, requiring legal review.
- **Desktop redistribution restrictions**: governed by the OEM EULA — the license file ships inside the product; extraction protection and compliance are product-security and legal obligations. **Requires an explicit EULA review before any commitment — not performed in this investigation (no license was procured).**
- **Offline capability**: OEM/perpetual yes (license file locally); metered no.
- **Deterministic-output capability**: undocumented, closed-source, unproven (§8). Aspose's own docs note MPP-format-version preservation on updates (2003–2021 formats) [E9] — evidence the writer is template/version-coupled rather than a free-form canonical serializer, which deepens (not resolves) the determinism question.
- **Vendor dependency**: single vendor, closed source, annual-renewal economics; the writer's output bytes can drift with every Aspose release and GenOffice could neither audit nor pin the semantics without re-running the §8 oracle each upgrade.
- **Long-term viability**: Aspose is a mature vendor with a broad office-format portfolio — low near-term disappearance risk, but the dependency converts a format capability into a recurring business relationship.

**Explicit statement required by the brief**: recommending or adopting Aspose.Tasks would change GenOffice's licensing/distribution architecture (first commercial runtime dependency in the Project stack, per-developer annual cost, EULA obligations, embedded license-file handling). This report does not recommend it. It is documented here as the ONLY conditional path IF true MPP export ever becomes a hard product requirement — gated on: an explicit business decision to fund the license, a legal EULA/redistribution review, a licensed feasibility spike proving §8's oracle determinism and §7's tier estimates, host-hardening for OS-level network isolation beyond Linux, and Principal Architect acceptance of a new host-side package. None of these has happened.

## 12. Browser/server implications

- **Browser**: no MPP-write strategy can execute in a browser. Aspose has no WASM SDK (its browser story is the Cloud REST API — the rejected exfiltration path); CheerpJ cannot help because MPXJ has no writer at all [E1][E2][E14]; COM is Win32-only. Web-hosted MPP export would therefore always be a server endpoint — which converts the product question into the server question below.
- **Server**: technically possible only via the commercial SDK (COM is explicitly unsupported server-side by Microsoft [E6]; the cloud SaaS is rejected on privacy). A server-side Aspose conversion endpoint would additionally inherit the metered-license network caller or embed an OEM license server-side, and would re-open the PROJECT-018 open question about server-side conversion endpoints and their privacy statements. GenOffice's web write story stays: generate MSPDI server-side or client-side with the foundation exporter — deterministic, license-clean, and host-neutral by construction (architecture-lock §3).
- **Determinism across hosts**: `.gproj`/MSPDI export produces identical bytes on desktop and web from the same canonical document (proven); no MPP strategy could make that statement (§8).

---

## 13. Product/distribution implications

- **Cost structure**: status quo adds zero cost. The commercial path adds US$2,397 + US$1,797/yr-class per developer and legal review; the COM path adds nothing in license terms but delivers a Windows-only feature fragment.
- **Feature-matrix consistency**: a Windows-only or desktop-only "Save as MPP" contradicts the cross-host product intent (architecture-lock §1: one host-neutral semantic model shared by desktop and web). MSPDI export is available on every host today.
- **User-visible meaning**: for recipients who own Microsoft Project, an MSPDI file opens directly — the practical difference between "MPP export" and "MSPDI export" is a file extension and the presentation-data tier (§7). For recipients without Project, neither format helps them; both require Project or a reader.
- **Support burden**: an MPP writer would generate support tickets of the class "Project says my file is corrupt" with a closed-source black box in the middle — un-diagnosable by GenOffice. The MSPDI path's diagnostics are first-party, staged, and already accepted.
- **Distribution**: the LGPL compliance kit for the MPXJ import sidecar is already documented (`packages/project-mpp-host/LICENSE-THIRD-PARTY.md`); the commercial path would add EULA text, license-file management, and vendor-update choreography to every release.
- **Documentation posture (adopted now, zero code)**: the supported answer to "how do I get an .mpp from GenOffice?" is: save as MSPDI (`.xml`) — Microsoft's designated interchange [E5] — and, if a true `.mpp` is required, open it in Microsoft Project and save-as MPP there (§3 #9). This is the same answer Microsoft gives for Project-for-the-web users [E8].

## 14. Architecture impact

- **Recommendation E requires no architecture change.** The accepted `ProjectFileAdapter` surface already carries the complete write story (`inspect`/`import`/`export` for `.gproj` and MSPDI); the foundation packages remain dependency-clean; `architecture-lock.md` is untouched by this investigation (asserted by the discipline suite, and by the verification step comparing the file against merged main).
- **`ProjectFileAdapter` fit**: no candidate MPP strategy would fit the foundation adapter contract any better than the import sidecar did — i.e. not at all inside `packages/project-file` (architecture-lock §13 forbids MPP parser/writer implementation code in foundation packages). Any future MPP export capability would live in a NEW host-level package (the `project-mpp-host` pattern): a one-shot converter process behind the existing foundation contract, with its own diagnostics family. That is a **proposed architecture addition** — documented here, NOT implemented: it would require a work-item authorization, a security posture (incl. network isolation on the platforms it must run on), and the §8 oracle as its verification instrument.
- **COM strategy architecture shape (proposed-only)**: a desktop-host-only integration module (Electron main-process surface), never web/server, never foundation — plus per-platform capability probing. Documented for completeness; rejected (§10).
- **No changes to any accepted semantics**: PROJECT-014 `.gproj`, PROJECT-015 import, PROJECT-016 export, PROJECT-017 report, PROJECT-018 import pipeline — all untouched by this increment (zero production code changed).

## 15. Recommended strategy

**Adopt outcome E: defer MPP export indefinitely; `.gproj` + MSPDI are GenOffice's supported write formats; the user-installed-Project workflow is the documented path to a true `.mpp`.**

1. **Retire MPP as a write target** in the work-item graph: the original PROJECT-019 definition ("MPP export; compatibility suite; exporter emits supported MPP semantics") is formally superseded by this decision record. The file-format family (014/015/016/018 + rescoped 019) remains complete for PROJECT-047's compatibility suite, whose charter is import/export regression-blocking over the SUPPORTED formats.
2. **Keep the one conditional door open, evidence-gated**: if true MPP export ever becomes a hard product requirement, the only viable route is the commercial-SDK strategy (§11), requiring: an explicit business decision to fund licensing, a legal EULA/redistribution review, a licensed feasibility spike proving the §8 oracle determinism and the §7 tier estimates, host-hardening for network isolation beyond Linux, and Principal Architect acceptance of a new host package. Until ALL of those happen, MPP export stays retired — no code, no dependency, no partial writer.
3. **Adopt the user-guidance posture now** (documentation, zero code): save-as-MSPDI is the Microsoft-designated interchange export [E5]; users requiring `.mpp` open the MSPDI in their own Microsoft Project and save-as MPP (§3 #9).
4. **Proposed (NOT implemented, requires authorization)**: a small follow-up UX increment — an `MPP_EXPORT_UNSUPPORTED` diagnostic family with actionable save-as-MSPDI guidance at the adapter-contract level, mirroring PROJECT-017 §17's original proposal. It would be the first and only production-code deliverable of the rescoped PROJECT-019, and only after the Principal Architect accepts this rescope.

## 16. Explicit rejected alternatives

1. **In-house MPP writer (native or pure-TS)** — undocumented proprietary format; the ecosystem's best-resourced reverse-engineering effort (MPXJ, ~20 years) still cannot write it [E1]; unknowable effort, no ceiling, no oracle for correctness.
2. **Extending the existing MPXJ sidecar to export** — the capability does not exist in MPXJ [E1][E2]; there is nothing to extend.
3. **Limited-subset MPP writer** — strictly worse than honest MSPDI: it would still be an MPP writer (all of #1's problems) while risking files Project rejects or silently misreads.
4. **Aspose.Tasks as a default dependency** — changes the licensing/distribution architecture (first commercial runtime dependency), annual per-developer cost, closed-source determinism hole, embedded license-file attack surface, metered-licensing network caller; disproportionate to a need already served by the sanctioned interchange format (§11).
5. **Aspose Cloud / any conversion SaaS** — data exfiltration boundary; no offline; recurring cost; requires separate architecture approval even to evaluate (§6).
6. **Microsoft Project COM automation as a product feature** — Windows-only, per-seat licensed, interactive, non-deterministic, server-side explicitly unsupported by Microsoft [E6][E7] (§10).
7. **Windows-only automation scoped as a desktop-only feature** — fragmented product matrix; all of #6's defects minus the server question.
8. **CheerpJ + MPXJ in the browser** — moot: MPXJ cannot write MPP regardless of runtime; plus commercial CheerpJ license and payload [E14].
9. **LibreOffice-mediated conversion** — LibreOffice has no MPP support at all [E13].
10. **ProjectLibre/other OSS tools as converters** — they embed MPXJ for READING; none write MPP.
11. **"MSPDI is basically MPP" marketing** — rejected as dishonest: the fidelity matrix (§7) shows exactly where they differ; the product promise must say MSPDI.
12. **A fake "export test" suite asserting MPP bytes** — explicitly forbidden by the brief; the discipline suite instead guards that NO writer exists (§17, tests).
